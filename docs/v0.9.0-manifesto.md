# The v0.9.0 manifesto: a game, not a machine

This document states the goal of the v0.9.0 milestone. It is subordinate to [the project manifesto](manifesto.md),
which it applies to one release, and it takes its design reference from [the Godot migration plan](godot-architecture.md).
Every v0.9.0 ticket is judged against this document: a change that leaves Core knowing less about the SNES is
progress toward v0.9.0, a change that leaves it knowing the same amount is not v0.9.0 work, and a change that teaches
Core anything new about the machine is rejected whatever ticket it serves.

Earlier work on umbrella #1302 isolated the hardware: typed views over emulated memories, boundary attributes on
every reach-in, catalogs of addresses and layouts, per-domain palette and VRAM views. That was the first step the
project manifesto describes under "The machine is removed, not encapsulated", and it was mistaken for the
destination. The umbrella's own notes waved the rest off: palette memory was "at most a rename", a register cache
"must stay byte-literal", Mode 7 and per-line effects "belong in the backend, no removal needed", and the address
catalogs were deferred to a cleanup that closed without touching them. v0.9.0 finishes the step that was started.

## 1. The goal in one paragraph

When v0.9.0 ships, `SuperMetroid.Core` is a C# game. A competent reviewer reading it cannot tell from the code that
it was not written from scratch as a native C# application, except inside a small, named set of compatibility
services that exist to reproduce gameplay-observable timing of the original hardware. The game plays WAV audio clips.
It renders PNG sprites, sprite sheets, metatiles and backgrounds, with every visual effect a shader parameter applied
by a GPU backend. Mode 7, windows, colour math, fades, per-line distortions and brightness are things the backend does
with its own shaders from an effect description; they are never registers, tables or memory images in the simulation.
There is no VRAM, CGRAM, OAM, DMA, HDMA, APU, SPC, DSP, CPU bus, bank, cartridge address or native word anywhere in
Core, and there is no software rasterizer anywhere in the product. The recorded SMV movies replay with full parity,
and the only place that parity timing lives is the compatibility services.

## 2. The test

Apply this test to any file in Core, any type, any member, any identifier:

> Would this exist, under this name, with this type, in a Super Metroid remake written in C# by someone who had
> never seen the SNES?

If yes, it is finished. If no, it is one of three things, and the change must say which:

| It is | What happens to it |
| --- | --- |
| **Incidental representation.** The 1994 program happened to store it this way: a 16-bit word, a palette slot number, a tile index, a code pointer, a DMA record, a register byte. | Deleted and replaced by the domain thing it stood for. |
| **A presentation quirk.** The hardware produced a visible artifact: sprite caps and overflow, per-part priority, OAM parking, exact scanline rasterization, stale tilemap strips, misaligned register stores that corrupt neighbours. | Deleted. The port does not preserve presentation quirks (owner decision, 2026-10-12). |
| **A gameplay-observable hardware behaviour.** The timing or value changes what the simulation does next: when a sound request is accepted, how far the door loader has progressed when an enemy initializes, a counter that wraps and is tested by its sign, a palette value an AI reads back, the input history a draw epilogue records, the point at which effect work advances the RNG. | Kept, as a compatibility service or a named stub, in domain terms, documenting the behaviour it reproduces and never the hardware it came from. |

"It is needed by the renderer" is not a fourth category. The simulation publishes a display model; the backend
learns to draw it. "It is needed by the replay" is not a fourth category either. The replay is driven by inputs and
the compatibility services; if parity depends on something, that something is a compatibility service.

## 3. What the game is made of

### Audio

Asset extraction renders every music track and sound effect to a PCM clip at export. The runtime holds a clip
library and a playback model: play, loop, stop, pitch, and the per-song echo bus. Sound requests go through a
request queue per sound library whose acceptance timing is a compatibility service. Nothing in Core knows what an
APU port, an SPC driver tick, an upload stream or a DSP register is. The upload addresses, bank identities and
port vocabulary leave Core; a music-data bank change is a clip-set switch with its documented downtime.

### Graphics

Asset extraction pre-assembles and pre-colours every piece of artwork under its standard palette: one sheet per
actor with every frame fully assembled, one image per boss part, pre-coloured metatiles per tileset, full images
for backgrounds and for every frontend screen's static content. The simulation selects a frame, a part or a tile
by semantic identity and places it. Colour effects (hit and freeze flashes, suit and charge palettes, beam and
visor palettes, palette-cycle glows, liquid tints, fades, colour math) are typed effect state the simulation owns
and publishes as shader parameters. The simulation never composes a frame from characters, never selects a colour
from a palette row, and never uploads tiles.

### The display model

Each accepted frame publishes one immutable display packet: ordered layers of placed images, metatile layers with
scroll, text, solid colours, and effect descriptions (camera, layer visibility, window shapes, blend modes,
per-line scroll or distortion, brightness, Mode 7 transform). It carries no memory image, no register value, no
object-selection byte, no priority ladder named after PPU background modes. The existing latched display boundary
(`StepCaptured`, `FrontendDisplay`) stays, because what is latched at frame end is gameplay-observable; what it
latches becomes the display model.

### The backend

One GPU backend, Direct3D 11, draws the display model: sprites and tilemaps as textured quads, effects as shaders,
Mode 7 as a shader over the floor image. It is an intermediate step: v1.0.0 ports each shader and composition rule
into Godot's own rendering. It exists in v0.9.0 because the simulation cannot be proven free of the hardware while a
software PPU still draws it. The software rasterizer, the Mode 7 rasterizer, the colour-math compositors and the
render-snapshot memory are deleted, not moved. The Android host goes dormant until the Godot port supplies it
(owner decision, 2026-10-20).

### Input

Controller state is typed buttons sampled once per admitted simulation step through the existing latch. Host device
types, bindings files, options files and recording formats are host concerns and live in the host.

### Hosts

Core publishes a display packet and an audio frame and consumes typed input. Everything that schedules, presents,
times, configures or recovers is the host's: frame mailboxes, presentation gates, deadlines, catch-up policy,
renderer selection, aspect correction, ini options, legacy save-file import, crash reporting. None of it is in Core.

## 4. The compatibility layer

A compatibility service is the only form in which hardware behaviour survives in Core. Its shape:

- It is a service or a value type with a domain name: a sound acceptance clock, a door-load progress policy, a
  wrapping countdown, an owned colour an entity reads back. Its name says what it does for the game, never what
  chip it imitates.
- It is injected into the entities and systems that need it, at the session composition root, with a lifetime
  matching the state it owns. The game runs against one implementation; verification may supply recorded evidence.
- Its XML documentation states the gameplay behaviour it reproduces, the point in the frame at which it is
  consulted or advanced, and the recording or source evidence that established it.
- It owns its own state. There is no memory image, port array, register byte or address behind it.

The existing session host-services record (door-music-upload timing, door-loader progress, sound acknowledgements,
frame publication) is the seed of this layer and the pattern new services follow. Each quirk gets its own service
only when it has its own timing contract; services with coherent responsibilities are preferred over one per field.

The behaviours that qualify are the ones [the Godot plan](godot-architecture.md) names as gameplay-observable: the
frame-end display latch, draw-time side effects that mutate simulation state, display state gameplay reads back,
sound acceptance and acknowledgement timing, door-transition load progression, wrapping and borrowing counters,
level-data allocation tails and bounded over-reads, and the exact sequence of RNG reads and advances including those
performed by effect work. A behaviour outside that list is not grandfathered in by being hard to remove.

## 5. What is deleted

By the close of v0.9.0 none of the following exists in Core:

- The `Hardware` module and its layer in `csharp/module-map.json`. Its domain-usable residue (an RGB colour type, a
  fixed-point number type, a wrapping countdown) is renamed in domain terms and moved to the module that owns it.
- Any type, member, identifier or namespace containing `Snes`, `Vram`, `Cgram`, `Oam`, `Obj`, `Dma`, `Hdma`, `Nmi`,
  `Apu`, `Spc`, `Dsp`, `Wram`, `Ppu`, `Native`, `Rom`, `Bank`, `Pointer`, `Address` or `Cartridge`, outside the
  compatibility layer's documentation of what it reproduces.
- Every `*RomData`, `*Addresses`, `*Pointers`, `*CodePointers`, `*Layout` and `*VramTransferDefinition` catalog.
  Definition data they held that the game needs (durations, speeds, shapes, colours, frame lists) stays in
  domain-named catalogs; every address, bank, pointer, slot, destination word and byte count goes to the
  AssetExtraction codec that decodes it once.
- Every enum whose members are backed by cartridge addresses and whose values are read, and every definition keyed
  by a native pointer. Identities are names with arbitrary values; artwork is bound by semantic frame identity.
- Every `ushort`, `byte` or `sbyte` holding gameplay state, except inside a named wrapping stub whose summary states
  the gameplay behaviour the width produces.
- Hexadecimal literals of four or more digits in functional code. A flag mask or a file-format constant keeps its
  allowance at its site, with the reason naming the thing.
- The hardware-boundary attributes and their analyzer families (`[CpuBusBoundary]`, `[PpuLayoutBoundary]`,
  `[SpcMemoryBoundary]`, `[DspRegisterBoundary]` and their access markers), their `docs/*-boundary.md` notes and
  `docs/*-inventory.json` files, deleted in the change that removes their last Core site. They were scaffolding;
  the project manifesto says scaffolding goes with its last consumer.
- The software renderer and everything only it consumed.

AssetExtraction keeps its knowledge of the ROM: it is the import pipeline and the one place an address may be named.
The vocabulary rule above applies to Core; the encoding and identity rules continue to apply to both.

## 6. Parity

Parity is proven the way it always has been: a single initial-state import followed by the converted input timeline
of each supplied SMV, replayed through production gameplay without desynchronization, per
[the replay contract](smv-gameplay-parity.md). v0.9.0 changes nothing about that contract. What it changes is where
the timing that makes parity hold lives: in the compatibility services, and nowhere else.

Replays are confirmation, not search. A ticket that replaces a hardware simulation with a compatibility service runs
the replay that exercises that service to confirm the service, as its focused check. Nobody runs the replays to see
what else broke; the loop-back ticket at the end of the milestone is the one place a whole-milestone replay pass is
authorized, and it is authorized there because the milestone's acceptance is that the replays pass with no hardware
left.

## 7. Acceptance

The milestone is complete when all of the following hold:

1. The vocabulary rule of section 5 is an analyzer at error severity in Core with zero findings and no allowances
   outside the compatibility layer.
2. The hardware-boundary analyzer families report zero Core sites and have been deleted with their documents.
3. The `Hardware` module is gone from Core and from the module map.
4. No type in Core holds a memory image, a register value, a port, an address, a bank or a pointer.
5. The software renderer does not exist; the Direct3D 11 backend draws the display model and nothing else.
6. The installation's artwork folder contains pre-coloured images for every drawn thing, and the audio folder
   contains clips for every sound; the runtime reads nothing else.
7. Every compatibility service is named in domain terms, injected at the composition root, and documents the
   behaviour it reproduces.
8. The supplied SMV replays pass through the Direct3D 11 host.

A ticket in v0.9.0 is not done while a rule it depends on has findings, an allowance it added would be equally true
of a thousand other sites, or a hardware type it was meant to delete still has a consumer.

## 8. Rules for agents on v0.9.0 tickets

Section 8 of [the project manifesto](manifesto.md) applies in full. In addition:

- **Classify before you touch.** For each hardware thing in the ticket's slice, record which row of the table in
  section 2 it falls in. Incidental and presentation are deleted. Gameplay-observable becomes a compatibility
  service. "Keep it because the backend reads it" and "keep it because a test asserts it" are not classifications.
- **Delete, do not relocate.** Moving a simulation out of Core into another product project is not progress unless
  that project is the backend drawing the display model. A software PPU in its own project is still a software PPU.
- **The backend learns to draw.** When the display model lacks something the picture needs, add the description to
  the model and teach the backend to draw it. Never reintroduce a memory image or a register so the backend can keep
  its current code.
- **Name the service for the game.** A compatibility service's name, members and documentation describe gameplay
  behaviour. If the only honest name is the chip's, the service has not been understood yet.
- **Nothing is deferred to v1.0.0.** The Godot port moves a finished C# game. A hardware thing left for "the Godot
  work to handle" is a v0.9.0 finding.
- **Report in the manifesto's terms.** For each batch: the slice, each hardware thing and its classification, what
  replaced it, the compatibility services added or changed with the behaviour each reproduces, the replay or
  focused check that confirmed it, and anything found that this document forbids.

## 9. After v0.9.0

v1.0.0 moves the finished game into Godot: the display model becomes scenes and resources, each Direct3D 11 shader
becomes a Godot shader or composition rule, the host becomes the Godot host, and the compatibility services are
carried over unchanged. The cost of v1.0.0 is set by how honestly v0.9.0 is done.
