# The compatibility layer

Core is a C# game (v0.9.0 manifesto). The one place behaviour of the original hardware survives in it is the
compatibility layer: a small set of services and value types, in the `SuperMetroid.Core.Compatibility` module, that
reproduce timing or values of the original machine which change what the simulation does next. Everything else that
came from the hardware is incidental representation or a presentation quirk, and is deleted (manifesto, section 2).

## Shape

- **Named for the game.** A service's type, members and parameters say what it does for the game: a sound acceptance
  clock, a room's load progress, a wrapping countdown. Never the chip it imitates; the vocabulary rule (SME6438,
  `docs/core-vocabulary.md`) holds for the layer's identifiers like any other Core code.
- **Marked.** Every type in the module carries `[CompatibilityService("behaviour")]`, whose argument is the gameplay
  behaviour reproduced. Its XML summary states that behaviour, the point in the update at which the service is
  consulted or advanced, and the evidence that established it (an SMV recording's trace, or the original routine).
  The summary may name the hardware behaviour it reproduces; identifiers may not.
- **Owns typed state.** A service holds its own state as domain values (requests, phases, counts). It never holds a
  memory image, a port array, a register byte or an address (SME6439 reports a byte or word array, span or memory
  field on a marked type).
- **Injected.** Session-scoped services are created or selected at the session's composition root
  (`SuperMetroidGameHostServices`, `FrontendSession`) with a lifetime matching the state they own. The game runs against
  one implementation; verification may supply recorded evidence through the same contract.
- **Value types** (a wrapping countdown) live in the module too and are used directly by the entities that own them.
- **Lowest module.** Every other module uses the layer (the wrapping counters are everywhere), so the layer depends on
  no other Core module: a service's contract is written in its own types, and the domain supplies its identities
  through generic keys. The sound services are generic over the library (`SoundAcceptanceClock<TLibrary, TSound>`):
  Audio's composition roots pass `SoundEffectLibraries.InQueueOrder`, the order each request check serves the
  libraries, and the library that reports a music load, and the clock finds a library by equality. The layer declares
  no library count and never reads an identity's value.

## What qualifies

Only behaviours the [Godot migration plan](godot-architecture.md) names as gameplay-observable (manifesto, section 4):
the frame-end display latch, draw-time side effects that mutate simulation state, display state gameplay reads back,
sound acceptance and acknowledgement timing, door-transition load progression, wrapping and borrowing counters,
level-data allocation tails and bounded over-reads, and the exact sequence of RNG reads and advances including those
performed by effect work. A behaviour outside that list is not admitted by being hard to remove. Each quirk gets its own
service only when it has its own timing contract; coherent responsibilities share one service.

## What does not qualify

- Anything kept "because the backend reads it": the simulation publishes a display model and the backend learns to
  draw it.
- Anything kept "because the replay needs it": the replay is driven by inputs and these services; if parity depends on
  something, that something is a service here, in domain terms.
- Presentation quirks (sprite limits, priority artifacts, raster timing): deleted, not preserved.

`LiquidWaveAndStatueDescent` (World, formerly `PerLineEffectPhase`, #1522) is classified as gameplay, not a service (#1479): advancing the room liquid and the Tourian
statues is the game's own work, and the compatibility behaviour it carries, its place in the random sequence, is
`EffectPhaseRandomOrder`'s. Its documentation states its frame point and evidence.

`WreckedShipGhostFade` (Enemies, #1512, #1544) is the Wrecked Ship ghost's own colour value rather than a service of this module, because its colours are the ghost's and the import pre-colours its shades by running it: its brightening raises all three channels of each colour in one addition, so a channel passing full carries into the next, and its fades step all sixteen of the ghost's colours, colour zero too, which no picture draws; when each ends decides when the ghost's AI moves on. Its documentation states the behaviour, the phases that consult it and the evidence.

The Samus over-read services are decoded by the import pipeline (`SamusOverreadFiles`) and reach the session with the
installed content as `SamusOverreadServices`; the gameplay runtime hands each to the owner that consults it as it builds
that owner (the projectile system, every Samus, the actor drawing, the opening cinematic's flashbacks).
The enemy over-read services are decoded the same way (`EnemyOverreadFiles`) and reach the session as
`EnemyOverreadServices`, which the runtime installs on its `EnemySession` with the rest of the installed content; an
enemy consults its service only on the path that reads past its data (#1500).

The boss and intro over-read services (#1500) are decoded the same way (`BossAndIntroOverreadFiles`) and reach the
session as `BossAndIntroOverreadServices`; the gameplay runtime binds them to its enemy session, and the opening
cinematic hands the shell's to its egg fragments:

| Service | Gameplay behaviour reproduced | Consulted |
| --- | --- | --- |
| `KraidNailPastLedges` | a fingernail 128 or more pixels above Kraid's body passes his four contour ledges and is pushed back at the record that follows them, which lies far beyond his right side; a nail past that record's bound is rejected, since terrain keeps every nail within Kraid's two-screen room (a bounded over-read) | a flying nail's update, when no wall reflected it and the nail lies above every ledge |
| `CrocomireTenthShotGradient` | the volley's last shot (spawn parameter 18) is aimed by the word after the nine authored gradients; parameters past 18 are rejected, since the spit attack stops counting at 18 (a bounded over-read) | the update after the last shot spawns, when it turns its aim into a velocity |
| `StoredExploredMaps<TArea>` (with `StoredExploredMapLoads` and `ExploredMapExchangeDoorDefinitions`) | a camera scroll check past the room's fifty scroll cells reads the explored maps the game last stored, area by area in runs of eight cells (none explored: red; only the run's last cell: blue; otherwise green); the service keeps the game's one live map, marked with every explored cell, and the eight stored maps, stored by the 31 doors whose elevator properties carry `$40` and by every save, loaded by those doors, file select and the Zebes landing, set by a file load and cleared by a new or cleared file, a demo (Zebes areas) and a soft reset; a read past the eighth stored map (a camera above a room nine or more screens wide) needs the whole of work memory and is rejected (a bounded over-read, #1336, #1500) | session-owned by `FrontendSession`, carried to each runtime's `SharedGameState` and its room scroll storage; consulted by the camera's scroll-boundary checks during Samus's scrolling |
| `ShellFragmentFallPastCurve` | the two highest egg-shell fragments fall by the three steps after the 38-step gravity curve before they land; later steps are rejected, since every fragment has landed by then (a bounded over-read) | a falling fragment's update once it has fallen for the whole curve, before the floor test |
