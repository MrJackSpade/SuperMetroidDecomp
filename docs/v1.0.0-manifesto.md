# The v1.0.0 manifesto: a Godot game, written new

This document states the goal of the v1.0.0 milestone and the rules for working on it. For v1.0.0 work it wins over
every other document in the repository, including [the project manifesto](manifesto.md) and
[the v0.9.0 manifesto](v0.9.0-manifesto.md), which describe the C# port and stop applying at the Godot project's
boundary.

Three documents govern the Godot project: this one, [the architecture guide](godot-architecture.md) and
[the type system](godot-types.md). Every other file in `docs/` describes the old code. Read those only to
understand what the old code does; none of their rules apply to Godot work.

Everything here is an owner decision. Section 7 lists what the owner has not decided yet.

## 1. The goal

v1.0.0 is Super Metroid written as a Godot game. It plays the same as the cartridge. It is not the C# port moved into
Godot, and it is not the 1994 program restructured: it is a new program, designed the way a Godot developer would
design this game today.

v1.0.0 is the complete conversion. The whole game works in Godot when it ships; nothing is left for a later version.

It is built as three layers, and the separation matters as much as the game does:

- **An engine.** The loop, collision, rooms and world logic, and every game system and piece of shared logic: the
  base enemy, the player controller, the projectile, pickup and item systems, the colliders. Its base classes
  distil what each kind of thing is. It contains nothing specific to Super Metroid. The owner will go on to build a
  different game on it.
- **Super Metroid, in code,** on top of the engine: only the particular things. Samus, each enemy, each item, each
  room, as thin classes on the engine's bases. This layer also holds the compatibility layer: the oddities of this
  game that no new game would want and that must stay out of the engine.
- **Super Metroid's assets,** produced from the player's ROM when the game is set up and never distributed. They are
  plain text, image and audio files in neutral formats, meant for the community to open and change. Anything of
  this game that can live in an external file does, values included: the project keeps behaviour and structure, the
  files keep the art, sound, layouts, numbers and words. Every value still shows in the Godot editor, read-only,
  on the thing it belongs to.

[The type system](godot-types.md) says what belongs in each layer.

Settled by the owner:

- The Godot project lives in `godot/`.
- It uses the latest stable Godot and the latest .NET that Godot supports, checked when the project is created.
- The existing asset extractor remains the program that turns a ROM into assets. It stays a separate program the
  Godot project never references. Its output changes to the engine's asset formats, which the engine defines.
  It reads the old code's definitions. (It was to become self-contained after parity, when the old code was
  deleted; the owner closed that plan on 2026-11-25, #2910: both games are kept and released, as Classic and
  Rebirth.)
- There is no save or recording compatibility with the C# port.
- It exports for Windows and for Android: the owner asked on 2026-11-25 for a signed Rebirth APK beside the
  Windows build, for testing on a handheld (#3258).
- Nothing of the port's analyzers carries over; the Godot project gets its own code analysis and rules later, when
  the owner sets them.

## 2. The C# port is documentation, not a blueprint

The C# port exists to tell you what the game does: its numbers, timings, rules, room contents, enemy behaviour and
quirks, in a form far easier to read than a disassembly. That is all it is for.

- Read it to learn **what happens**. Do not copy **how it is organised**.
- No C# port code is reused. The Godot project lives in its own directory and has no references to the old code: no
  project reference, no shared source, no copied files, and no types, names, class layout, call order or state
  fields ported one for one.
- The old code is not deleted. It stays in the repository as the legacy reference.
- The port still follows the 1994 program's design in many places: fixed slot tables, one flat list of poses, a speed
  held as a size plus a separate direction, state spread over loose flags, routines that all work on one shared state
  object, per-frame phases named after the original's routines. Those are things the port inherited, not things the
  game needs. They are not carried into Godot.
- If the port does something in an awkward way, assume the awkwardness is inherited and design it properly. Keep an
  awkward structure only when you can name the thing the player would see change without it.

**Nothing comes across unexamined.** This applies to everything in the old code, with no exceptions: every type,
service, rule, special case and comment.

- What is taken from the old code is a fact about the game: a number, a timing, a behaviour, an outcome. Never a
  piece of code and never a shape.
- Each fact is re-examined before it is used. Is it something the game does, or something the old code did to
  itself? Is it something the player can observe?
- It then goes into the new project only in the shape [the type system](godot-types.md) gives it. If the old code
  holds it in a shape that is not the new architecture's, it is rewritten in the new shape. It is never adapted,
  wrapped or copied to save the rewrite.
- That the old code names something, documents it at length, or gives it its own class is not evidence that the new
  project needs it. The old code's compatibility services are the plainest case: each one is a claim to check, not
  a service to rebuild.

## 3. The test

For any piece of the Godot project, ask:

> Would a developer building this game in Godot today, who knew exactly how it should play but had never seen the
> original code, build it this way?

If not, it is one of:

| It is | What happens |
| --- | --- |
| **Original design.** The 1994 program, or the port after it, happened to be organised this way. | Not carried over. Design it new. |
| **A quirk the player can observe.** The behaviour changes what happens in play. | Kept, in the one place it belongs (section 5). |
| **Out of scope.** It needs unbounded memory corruption (AGENTS.md, "Emulation scope limits"). | Dropped. |

"The port does it this way" and "the replay compared it" are not reasons to keep a structure.

A second question decides the layer, for every line:

> Would a different metroidvania built on this engine want this, unchanged?

Yes: it is engine. No: it is this game's. Something odd that only this game wants, but that touches what the engine
owns, is the compatibility layer's (section 5).

## 4. What "plays the same" means

Parity is judged on what the player can observe, not on how the program is organised inside.

- Given the same inputs, the game produces the same results on every update: where things are and how they move,
  energy and ammunition, what is hit, hurt, killed, spawned and collected, random outcomes, room and progress changes.
- How the program gets there is free. Internal order, internal state and intermediate values may differ from the
  original and from the port wherever the result is the same.
- The recorded movies remain the check. They are compared on those observable results. They are not compared on the
  original's internal memory cells (handler words, pose history, slot variables, instruction pointers, sprite
  tables), because comparing those forces the Godot game to have the same insides as the 1994 program.
- Hardware lag stays eliminated, and presentation quirks of the hardware stay out, as in the port.
- **No gameplay difference is acceptable.** The owner's rule: nothing can differ from cartridge behaviour. The first
  test will be a recorded movie played through the Godot game, which needs frame-by-frame accuracy of gameplay
  everywhere, in play and out of it. A known gameplay difference is a defect with its own ticket in the v1.0.0
  milestone, not a note in a report. Presentation ranks below clean, idiomatic code and is not matched at its cost
  (AGENTS.md, "Full parity with the cartridge is required").

**The replays are off limits until the owner opens testing.** While the project is being designed and built, the
agent does not run the recorded movies, read their traces, build replay tooling for the Godot game, or shape any
design around passing them. The architecture is decided on its own merits first. The owner says when the project is
architected and ready for replay testing; nothing before that point is checked against a movie.

## 5. Quirks live where they belong

- A quirk that belongs to one thing lives in that thing. A counter that wraps is a small counter type that wraps
  itself. A boss's odd hit rule is in that boss. A shot's odd starting position is in the shot code.
- Anything that can be isolated to its own class or instance is.
- A shared service exists only for a concern that really cuts across unrelated systems, where the systems must agree
  on one piece of state or timing. It is not a place to collect every quirk, and nothing is put in one just because
  it came from the hardware.
- Do not create static helper services for things a type can do for itself.
- A quirk never goes in the engine. One that belongs to a single enemy, item or object of this game is ordinary code
  in that thing, with a one-line comment saying what it reproduces.
- The compatibility layer is only for a quirk of this game that touches something the engine owns. The engine does
  the plain thing by default and offers a narrow, named place to supply something else; the compatibility layer, in
  the game's code, supplies it. It is small, it is the only such place, and it is not where quirks go by default
  (type system, section 1).

## 6. Rules for agents

- **The owner makes the rules; the agent builds on them.** There are two different things here.
  - *Building out what is defined* is the agent's job. The type system and the architecture guide are not complete
    and are not meant to be. Each section ends with a note saying why it is the way it is and how to extend it, and
    the type system's section 0 gives the reasoning behind all of them. When the work meets something they do not
    cover, the agent extends them by that reasoning, builds it, and writes the extension into the document in the
    same change. It does not stop to ask.
  - *Changing the rules* is the owner's. The agent does not alter what a section is for, weaken or reinterpret a
    rule, add a rule of a new kind (a check, a ban, a process), or change this manifesto. If an extension would only
    work by breaking something already written, that is a rule change: stop and ask.
  - The test: an extension makes the same moves the documents already made, and leaves everything already written
    true.
- **No analyzers move over.** The port's analyzers, audits and cleanup were deleted after v0.9.0 and are not ported.
  The Godot project's own code analysis and rules come later, when the owner sets them; do not write any before.
- **No word bans.** Write comments and names in plain English. Say "SNES", "the original" or "the cartridge" when
  that is the clearest way to explain why something is the way it is. Keep comments short. No ticket numbers in code.
- **Design first.** Before building a slice, write down what it must do (from the port and the references) and how
  it will be built in Godot. If the design looks like the port's class list, start again.
- **Extend the system that is defined.** [The type system](godot-types.md) lists every kind of type and gives the
  questions that decide where a thing belongs and who owns a behaviour. Apply them. Do not invent a different
  structure beside it.
- **Who may take what.** Work that needs architecture, design or new building, or that affects many systems, is for
  the newest Fable only. Isolated work with a clear fix may be taken by the newest Opus. Tickets say which by the
  labels `high` and `low` (AGENTS.md, "Which model takes a ticket"). The point is to keep the architecture from
  being poisoned, not to judge whether a fix is right.
- AGENTS.md still governs tickets, testing ownership, commits, error handling and reporting.

## 7. Not yet decided by the owner

Ask before assuming an answer to any of these:

- For when the owner opens replay testing, not before: whether the movie check may also compare the original's
  internal values (pose numbers, routine selectors, slot variables) as a debugging aid that never fails a run, or
  compares observable results only.
